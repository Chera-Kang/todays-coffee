# Git 작업 및 버전 거버넌스 규칙 (Git Workflow & Semantic Versioning Rules)

이 문서는 '오늘의커피(Todays-Coffee)' 프로젝트의 형상 관리, 버전 넘버링, 배포 및 보안 거버넌스 규약입니다.
어떤 에이전트라도 본 저장소에서 작업할 때는 본 규약을 100% 최우선으로 준수해야 합니다.

---

## 1. 🛑 커밋 및 푸시 사전 승인 원칙 (Strict User Authorization)
- **자동 커밋/푸시 절대 금지**: 체라님의 명시적인 요청이나 승인이 없는 한, 에이전트는 **절대로 임의로 `git commit` 또는 `git push`를 실행하지 않습니다.**
- **명시적 요청 시에만 실행**: 오직 체라님이 "커밋해줘", "깃허브에 올려줘", "git push 진행해줘" 등 명시적으로 지시한 경우에만 git 변경 작업을 수행합니다.
- **선 제안 후 실행**: 작업을 완료했더라도 실행할 명령어와 커밋 메시지 전문을 체라님께 먼저 보여드리고 확인을 받은 후 실행합니다.

---

## 2. 🔐 사전 민감정보 및 빌드 아티팩트 점검 의무 (Security Audit)
커밋 및 푸시 요청을 받았을 때, 에이전트는 `git add` 및 `git commit`을 실행하기 전 **반드시 아래 체크리스트를 전수 검증**해야 합니다:

1. **`git status` 확인**: 커밋 대상 파일 목록을 전수 검토합니다.
2. **민감정보 및 빌드 파일 포함 여부 전수 차단**:
   - ❌ 환경 변수 및 시크릿: `.env`, `.env.*`, `*.pem`, `*.key` (`.env.example` 제외)
   - ❌ 종속성 및 빌드 산출물: `node_modules/`, `dist/`, `.vite/`
   - ❌ 임시/개인 작업 파일: `*.tmp`, `todo.txt`, `prompts/` (로컬 전용 프롬프트 파일)
3. **만약 민감/빌드 파일이 추적(Tracked) 상태라면**:
   - 커밋을 즉각 중단(Fail-safe)하고, 체라님께 알린 후 `git rm --cached` 및 `.gitignore`를 점검합니다.

---

## 3. 🏷️ 버전 기반 커밋 메시지 컨벤션 (Semantic Versioning Tracking)
커밋 메시지는 반드시 대상 프로덕트 버전 태그(`[MAJOR.MINOR.PATCH]`)를 선두에 기재하고, 작업 사유 또는 표준 대체문구를 명시합니다:

### 1) 메시지 기본 포맷
- `[MAJOR.MINOR.PATCH] 작업 사유` (명확한 신규 기능/마일스톤 작업인 경우)
- `[MAJOR.MINOR.PATCH] 대체문구: 상세 내용` (단순 수정/유지보수인 경우)
- **예시**:
  - `[1.0.0] 정식 릴리즈: 8대 브랜드 45종 음료 큐레이션 및 에디토리얼 아키텍처 v1.0 완성`
  - `[1.0.1] 버그수정: Safari 모바일 뷰포트 바텀시트 스크롤 튐 현상 개선`
  - `[1.0.2] 코드개선: menus.json BVA 경계값 데이터 식별자(data-testid) 보강`
  - `[1.0.3] 테스트구축: Playwright 기반 코어 스모크 및 3단계 점진적 TC 자동화`
  - `[1.1.0] 큐레이션 고도화: 두 음료 1:1 맞대결 비교 팝업(VS Mode) 구축`

### 2) 버전 넘버링 증가 규칙
- **시작 번호 (Baseline)**:
  - 초기 1~5차 고도화 완료 시점을 기준으로, 첫 시맨틱 커밋은 **`[1.0.0]`** (정식 릴리즈 베이스라인)으로 기록하며, 다음 커밋부터 `[1.0.1]`로 순차 증가합니다.
  - (이미 이전 커밋에 `[1.0.0]`이 존재한다면 직전 패치 번호에서 +1 증가)
- **PATCH (자잘한 일상 업로드 / 버그 수정 / 테스트 코드 작성)**:
  - 커밋 및 푸시가 발생할 때마다 패치 번호를 1씩 자동 증가시킵니다 (`1.0.1` ➔ `1.0.2` ➔ `1.0.3` ...).
- **MINOR (로드맵 마일스톤 완료 및 배포)**:
  - `next_plan.md`에 명시된 기능 트랙(Track 1 웰니스, Track 2 1:1 비교, Track 3 축제 지도 등)이 완성되어 배포 판정을 내릴 때 마이너 번호를 올리고 패치는 0으로 리셋합니다 (ex. `1.0.8` 완료 ➔ `1.1.0` 착수).
- **MAJOR (대규모 도약)**:
  - PWA 오프라인 앱 배포, 전용 백엔드/DB 구축, 서비스 아키텍처 전면 개편 시 메이저 번호를 올립니다 (ex. `2.0.0`).

### 3) 표준 대체문구 작성 기준
특별한 대규모 신규 기능이 아닌 경우 다음 표준 대체문구를 선두에 활용합니다:
- `버그수정`: UI 깨짐, 스크롤 튐, 수치 계산 오류 교정
- `코드개선`: 컴포넌트 리팩토링, 성능 최적화, CSS/타이포 스타일 정돈
- `테스트구축`: Playwright E2E 스크립트, TC 추가, Self-Healing PoC 실습
- `문서수정`: README.md, next_plan.md, 규칙 파일 갱신

## 4. 🤖 에이전트 자동 판정 및 실행 프로세스 (Automated Resolution Workflow)
체라님이 "깃에 올려줘", "커밋하고 푸시해줘" 등 명시적 요청을 할 때, 체라님이 버전과 메시지를 직접 지정하지 않더라도 에이전트가 아래 흐름으로 자동 판정하여 수행합니다:

1. **이전 버전 자동 추적**:
   - `git log -n 5 --pretty=%B`를 확인하여 직전 커밋 메시지의 버전 태그(예: `[1.0.0]`)를 읽어옵니다.
   - 직전 커밋에 `[MAJOR.MINOR.PATCH]` 형태가 없다면 베이스라인 **`[1.0.0]`**을 부여하고, 있다면 다음 패치 번호(예: `[1.0.0]` ➔ `[1.0.1]`)를 자동으로 계산합니다.
2. **변경점 분석 및 메시지 자동 산출**:
   - `git status` 및 `git diff --stat`을 분석하여 이번 작업의 핵심 성격을 파악하고, 사유 또는 표준 대체문구를 조합해 완전한 메시지를 작성합니다.
3. **사전 보안 감사 (Rule 2) 실행**:
   - `.env`, `node_modules/`, `dist/` 등 민감/빌드 파일 포함 여부를 확인합니다.
4. **체라님께 사전 승인 요청**:
   - 이번에 부여할 커밋 메시지와 실행할 Git 명령어를 명확히 제안하고 체라님의 확인을 받습니다.
5. **Commit & Push 실행 및 보고**:
   - 승인 후 커밋 및 푸시를 실행하고 최종 커밋 해시와 상태를 보고합니다.

---

## 5. 🛡️ 브랜치 보호 (Branch Safety)
- `main` 브랜치에 대한 강제 푸시(`git push --force`, `git push -f`)는 어떠한 경우에도 절대 실행하지 않습니다.
- 기존의 과거 커밋 히스토리는 건드리지 않고 원형 그대로 보존합니다.
